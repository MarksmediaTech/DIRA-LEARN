## 0. Current production state and the fix (21 Nov 2026)

**Found in production:** migrations 01–37 were applied. The seed then failed with `ERROR: 42P01: relation "customers" does not exist`. The signed-in Super Administrator's profile (`super_admin`/`active`) returned **403** on `/rest/v1/profiles`, so the app stayed on "Loading your account…".

**Cause of the 403 (confirmed):** migrations 01–37 never granted table privileges to the API roles. They relied on Supabase granting every new table automatically. Supabase stopped doing that for new projects on 30 May 2026 and for all projects on 30 Oct 2026. Reproduced locally on 21 Nov 2026: with Supabase's current default, a `super_admin`/`active` account gets `permission denied for table profiles`, and only 5 of 106 tables are readable by signed-in users. **Migration 38** writes all grants explicitly: signed-in users get only what an RLS policy allows; signed-out visitors get no table at all.

**The `customers` error:** not from DIRA LEARN. No migration, seed or function in any version refers to a `customers` table. Checked: 223 files across every version (V8, the release-check upload, the full archive), the whole git history and all briefs. The only matches are lesson wording such as "turn engagement into customers". The seed itself completes on an empty test database. To find the script that was run: Supabase dashboard → SQL Editor → open the query history and look for a query that mentions `customers`. Alternatively, Logs → Postgres, around the time of the failure.

**What to do:** section 6b. Run the read-only pre-check `00b_precheck_partial_readonly.sql`, back up, run `01b_continue_after_37.sql` (migration 38 + the seed), then verify. Existing accounts, passwords, roles and statuses are kept. Because an active Super Administrator already exists, the first-admin claim (section 7) is not needed, and verification checks 7 and 8 report `FAIL` by design.

## 1. What is wrong, and what this fixes

`select to_regclass('public.profiles')` returns NULL in production, and the browser receives 404 (PostgREST `PGRST205`, unknown table) for `/rest/v1/profiles`. So the repository migrations were never applied to this project. Supabase Auth works on its own (`auth` schema), which is why people can register and verify. But DIRA LEARN itself has no tables, functions, Row Level Security policies, storage buckets or sign-up trigger. The website then cannot load any account.

Since the fix of 20 Nov the website shows *"We could not load your account"* with the error code instead of loading forever. But only initializing the database fixes the real problem.

The fix is to apply the **existing** repository migrations `01`–`37` and `seed.sql`, unchanged and in order. No new schema is invented. The bundle in `supabase/production_init/` is these files byte for byte. Its header lists their SHA-256 hashes, and around them it adds only a safety guard, transaction boundaries and migration-history rows.

### Objects that sign-in and account loading need

- **Tables:** `profiles` (01), `organizations` (01), plus the restrictive policies from 34.
- **Trigger:** `on_auth_user_created` on `auth.users` → `handle_new_user()` (02, re-created by 36).
- **Foreign key:** `profiles.id` → `auth.users(id)` on delete cascade (01). The primary key on `profiles.id` makes a duplicate profile impossible, and `handle_new_user()` uses `on conflict (id) do nothing`.
- **Functions:** `app_role()`, `is_staff()`, `is_admin()`, `account_is_active()`, `check_request()` and the profile guard triggers, plus `first_admin_needed()` and `claim_first_admin()` for setup.
- **RLS policies on `profiles`:** a user reads and updates only their own row. Staff, trainers and mentors read what their role allows. Only administrators can change roles, and the guard triggers stop self-promotion.
- **Edge Function:** `claim-first-admin`, only for the one-time first administrator (section 7). Sign-in itself needs no Edge Function.

## 4. Data preservation

Checked in the migration text and in the local rehearsal:

- **`auth.users` rows are never modified.** That covers emails, password hashes, confirmation state and metadata. The rehearsal compares a hash of these columns before and after, and they are identical. The only change on `auth.users` is the new trigger.
- **No migration drops or truncates a table.** The only `delete` statements are inside functions (Connect retention in 22/25 and officer changes in 24), which run only when called later in the app.
- **Existing accounts:** migration 36 gives each account without a profile one profile with role `applicant` and status `active`. That is the lowest access in DIRA LEARN, and exactly what the sign-up trigger gives a new account. It is recorded in `profile_repair_36_backup`. Unverified accounts get the profile too, but still cannot sign in until they verify.
- **Nobody becomes an administrator.** After initialization, every profile is `applicant`. Verification check 7 confirms this.
- **Curriculum:** the initialization approves nothing new. It seeds exactly the approval state recorded in the repository (section 4a). Verification checks 13 and 14 confirm this.

## 5. Impact of running it (please read before approving)

When the initialization runs in production:

1. **100 tables, about 225 functions, views, RLS policies on every table, and 6 private storage buckets** are created in `public`/`storage`. The `supabase_migrations` schema records migrations 01–37.
2. **The sign-up trigger becomes active.** Every new registration gets its applicant profile automatically.
3. **Existing accounts:** the people who already registered can sign in and see the applicant pages, instead of the error screen. They get no other access.
4. **API-wide account-status check (34).** Every Data API request first runs `check_request()`. Suspended or deactivated accounts are refused. For active users nothing visible changes.
5. **Realtime:** the DIRA Connect tables are added to the `supabase_realtime` publication.
6. **Downtime:** none is needed, because the site cannot load accounts now anyway. It takes seconds locally. Allow a few minutes on Supabase.
7. **Not affected:** the Cloudflare site, Auth settings, SMTP, Edge Functions, secrets and existing passwords. No paid service is involved.

**Rollback.** Before initialization the public schema is empty, so the backup from step 6.1 is the authoritative undo. Rollback scripts exist for 23–37 (`supabase/rollback/`), newest first. Undoing the whole initialization would mean dropping the created objects, which also deletes any data entered afterwards, so do it only after talking it through.

## 6. Procedure

You need: the Supabase dashboard, a terminal with `npx` (Node 20+) **or** `psql` 15+, and the database password (Dashboard → Project Settings → Database). Do not paste the password, connection string or any key into chat or into a committed file.

### 6.1 Back up (before anything else)

Your accounts are the only data in production. Keep the dumps somewhere private, never in the repository, because they contain password hashes.

```bash
npx supabase login
npx supabase link --project-ref kzbgfofklkqahfffwyzz          # asks for the database password
npx supabase db dump --linked -f backup_schema_before.sql
npx supabase db dump --linked --data-only -f backup_data_before.sql
# extra copy of the accounts themselves, with psql/pg_dump 15+ and the session-pooler connection string:
pg_dump "<connection string>" --schema=auth --data-only -f backup_auth_before.sql
```

If the project is on a paid plan, also confirm that a recent backup is shown under Dashboard → Database → Backups.

### 6.2 Pre-check (read-only)

Dashboard → SQL Editor → paste `supabase/production_init/00_precheck_readonly.sql` → Run.

- **`SAFE_TO_INITIALIZE`:** continue.
- **`STOP`:** do not continue. Send the table to Claude. It shows only counts and object names, no personal data.

### 6.3 Initialize: choose ONE option

**Option A, Supabase CLI (recommended; standard tooling, records history itself):**

```bash
npx supabase db push --linked --dry-run          # must list exactly the 39 migrations 01..39 and nothing else
npx supabase db push --linked                    # applies them, each in its own transaction
```

Then run the seed. Dashboard → SQL Editor → paste `supabase/seed.sql` → Run, once. (`db push --include-seed` also works on CLI versions that have that flag. Check `npx supabase db push --help` first.) If your CLI version wants `--remote` instead of `--linked`, as some earlier notes in this repository say, use that. `--help` shows which one it has. The CLI could not be run here (no package registry), so its exact flags were not tested.

**Option B, the single bundle with psql:**

```bash
psql "<session-pooler connection string>" -v ON_ERROR_STOP=1 -X -f supabase/production_init/01_initialize_production.sql
```

The last output is a one-row summary. Expected values: `migrations_recorded 39`, `accounts_without_profile 0`, `profiles_above_applicant 0`. The bundle is 1.7 MB, too large to paste into the SQL Editor in one go. **To install in the browser only (no psql), use the six-part SQL Editor version instead: `docs/deployment/SQL_EDITOR_INITIALIZATION.md`.** It is the same migrations and seed, byte for byte, validated to produce the identical database.

**If something stops half-way (either option):** every migration before the failing one is applied and recorded. Nothing of the failing one remains. **Do not re-run the bundle.** Send the error to Claude. Once the cause is fixed, `npx supabase db push --linked` applies only the remaining migrations. The local rehearsal tests this resume path.

## 7. First administrator: claim-first-admin and SETUP_CODE

Do this only after 6.4 says `READY`. It grants super administrator to exactly one existing applicant account, the one that is signed in when the code is entered.

1. **Create the setup code on your own computer.** It must be at least 20 characters. Do not reuse a password, and do not send it in chat or email.
   - macOS/Linux: `openssl rand -base64 32`
   - Windows PowerShell: `[guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')`
2. **Set the secrets** for the function. Do this in the terminal or in Dashboard → Edge Functions → Secrets, not in any file:
   ```bash
   npx supabase secrets set SETUP_CODE='<the code>' --project-ref kzbgfofklkqahfffwyzz
   npx supabase secrets set APP_URL='https://dira-learn.marksmedia-studios.workers.dev' --project-ref kzbgfofklkqahfffwyzz
   ```
   `APP_URL` is required. The functions only accept browser calls from that origin (CORS, no wildcard). Without it, `/setup` fails with "This website address is not allowed". `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are provided to Edge Functions by Supabase automatically. Never put the service-role key anywhere else.
3. **Deploy the function** (deploying changes no database data):
   ```bash
   npx supabase functions deploy claim-first-admin --project-ref kzbgfofklkqahfffwyzz
   ```
   Keep JWT verification on (the default). The function also refuses anyone who is not signed in.
4. **Claim:** sign in as the person who should be the first Super Administrator, open `/setup`, and enter the code. The function checks the code in constant time, adds a 1-second delay after a wrong code, and works only while no active super administrator exists. A second claim is refused.
5. **Close setup immediately afterwards:**
   ```bash
   npx supabase secrets unset SETUP_CODE --project-ref kzbgfofklkqahfffwyzz
   ```
   With no code set, the function answers "First-time setup is switched off".
6. **Founder and Co-Founder:** the new Super Administrator assigns those roles in the app (User Management). Migration 17 gives them administrative permissions equivalent to Super Administrator. Do not change roles with SQL.
7. Re-run `02_verify_readonly.sql`. Check 7 (nobody above applicant) and check 8 (`first_admin_needed`) now correctly say `FAIL`, because one administrator exists. Checks 14 and 15 likewise say `FAIL` once the 11 Digital Marketing topics have been approved in the Curriculum Approval Centre. Every other row must still say `ok`.

The other Edge Functions (`invite-user`, `send-emails`, `email-webhook`, `scan-attachments`, `set-account-status`, `import-learners`, `convert-application`) are not needed for sign-in. Deploy them separately, following `DEPLOYMENT_CHECKLIST.md`, each after its own impact check.
